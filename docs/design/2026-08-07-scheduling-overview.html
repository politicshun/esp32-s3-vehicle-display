ESP32-S3 차량 클러스터 · 설계 정리

여러 통신이 동시에 일어날 때 스케줄링은 어떻게 도는가

CAN 수신·CAN 송신·BLE·화면 렌더링이 한 칩 위에서 같이 돌아갑니다. 무엇이 무엇을 밀어낼 수 있고, 어디가 서로 닿아 있으며, 한쪽이 잘못됐을 때 나머지가 어떻게 되는지 정리합니다.

작성 2026-08-07 근거 main/main.c · twai.c · lvgl.c · ble.c · vehicle_data.c · sdkconfig 검증 실기기 COM12 + Kvaser Leaf v3

통신은 코어 0, 화면은 코어 1. 둘이 닿는 곳은 뮤텍스로 보호된 공유 구조체 하나뿐입니다.

CAN과 BLE는 같은 코어(0)에서 우선순위로 경쟁하고, LVGL 렌더링은 코어 1을 사실상 혼자 씁니다. 그래서 화면이 아무리 무거워져도 CAN 프레임을 놓치지 않고, 반대로 통신이 몰려도 화면 주사율이 떨어지지 않습니다. 대신 두 코어가 만나는 접점이 정확히 한 곳 있고, 그 지점의 성질이 이 구조 전체의 안전성을 결정합니다.

1. 누가 어느 코어에서 도는가

우선순위는 숫자가 클수록 높고, FreeRTOS는 우선순위 선점형입니다. 높은 우선순위 태스크가 준비 상태가 되면 낮은 쪽을 즉시 밀어냅니다.

태스크 코어 우선순위 주기 대기 방식 출처
bt_controller CORE 0 23 무선 이벤트 — ESP-IDF
esp_timer CORE 0 22 타이머 만료 — ESP-IDF
nimble_host CORE 0 21 BLE 이벤트 — ESP-IDF
twai_rx CORE 0 10 프레임 도착 시 twai_receive(1000ms) main.c
twai_tx CORE 0 9 500 ms vTaskDelayUntil main.c
ble_sync CORE 0 5 500 ms vTaskDelay main.c
lvgl_ui CORE 1 5 20 ms 목표 vTaskDelay(20ms) main.c
BLE 컨트롤러와 NimBLE 호스트는 CONFIG_BT_CTRL_PINNED_TO_CORE_0 / CONFIG_BT_NIMBLE_PINNED_TO_CORE_0으로 코어 0에 고정돼 있습니다. 우선순위 21·22·23은 configMAX_PRIORITIES = 25 기준의 IDF 기본값입니다. FreeRTOS 틱은 100 Hz이므로 모든 지연의 분해능은 10 ms입니다.

2. 전체 그림

네 개의 애플리케이션 태스크가 하나의 공유 구조체에서 만납니다. 코어 경계를 넘는 화살표는 그중 하나뿐입니다.

3. 동시에 몰리면 실제로 무슨 일이 일어나는가

코어 0 — CAN과 BLE가 경쟁하는 곳

BLE 스택(21·23)이 CAN 태스크(10·9)보다 훨씬 높습니다. 그래서 무선 이벤트가 발생하면 CAN 처리가 즉시 밀려납니다. 얼핏 위험해 보이지만 실제로는 문제가 되지 않습니다. TWAI 컨트롤러가 프레임을 받으면 ISR이 하드웨어 RX 큐에 먼저 넣기 때문입니다. twai_rx 태스크는 그 큐에서 꺼내기만 하므로, 태스크가 몇 밀리초 밀려도 프레임은 큐에 그대로 남아 있습니다.

따라서 실제 한계는 "태스크가 밀리는 시간"이 아니라 "큐가 5개를 넘기기 전에 태스크가 돌아오는가"입니다. 수신 대상이 0x100(초당 10회)과 0x200(초당 5회)뿐이라 큐가 가득 차려면 태스크가 약 330 ms 동안 한 번도 못 도는 상황이어야 합니다. BLE 이벤트 처리는 그보다 두 자릿수 짧습니다.

같은 우선순위끼리는 라운드로빈으로 10 ms씩 번갈아 돕니다. 다만 코어 0에서 우선순위 5는 ble_sync 하나뿐이라 실제로 발생하지 않습니다.

코어 1 — 렌더링 전용

lvgl_ui가 코어 1에서 사실상 혼자 돕니다. 통신 태스크가 아무리 바빠도 화면 갱신을 밀어내지 못하고, 반대로 렌더링이 아무리 무거워도 CAN 수신에 영향을 주지 않습니다. 이 코어 분리가 이 구조의 핵심 설계 결정입니다.

다만 현재 렌더링은 코어 1을 여유 있게 쓰고 있지 않습니다. 아래 실측을 참고하십시오.

측정 항목 실측값 의미
CAN 수신 최대 부하 초당 15 프레임 어셉턴스 필터가 0x100/0x200만 통과시키므로 버스가 아무리 붐벼도 이 값이 상한입니다.
CAN 송신 초당 2 프레임 ClusterAlive 0x300, 500 ms 고정.
BLE notify 초당 2 회 × 2 바이너리 + 텍스트 characteristic 각각.
lv_timer_handler 1회 평균 33 ms 20 ms 예산 초과 — 매 프레임 초과합니다.
렌더 루프 한 바퀴 평균 60 ms 실효 약 17 fps. 코어 1의 약 55 %를 렌더링이 점유합니다.
패널 플러시 평균 0.65 ms 병목은 전송이 아니라 LVGL 소프트웨어 래스터라이즈입니다.
실기기 부팅 로그(COM12)의 frame timing 진단 출력 기준. 이 진단 로그 자체가 main/lvgl.c에 임시로 들어가 있는 코드입니다.
여유가 없는 쪽은 통신이 아니라 렌더링입니다. 코어 0은 초당 19 프레임 남짓을 처리하면 되지만, 코어 1은 매 프레임 예산을 넘기고 있습니다. 통신을 더 얹어도 스케줄링상 문제가 없는 반면, 화면 요소를 더하는 쪽은 즉시 프레임레이트로 나타납니다.

4. 서로 닿아 있는 지점

코어를 나눠도 자원을 공유하는 곳에서는 다시 만납니다. 현재 네 곳입니다.

공유 자원 누가 쓰는가 점유 시간 위험도
xVehicleMutex 네 태스크 전부 (코어 경계를 넘음) 구조체 복사만, 마이크로초 단위 낮음
s_twai_lock twai_rx ↔ twai_tx 드라이버 재설치 시에만 길어짐 낮음
I2C 버스 (GPIO 8/9) GT911 터치 · CH422G 확장기 CH422G는 부팅 시에만 접근 낮음
UART0 콘솔 로그 모든 태스크 한 줄당 약 7 ms, 락으로 직렬화 현재 가장 큼
UART 로그가 유일하게 실질적인 경합입니다. twai_rx가 프레임마다 raw 덤프를 찍고 있어 초당 약 100 ms를 UART 출력에 씁니다. 벤치 테스트용으로 HARNESS-TODO 표시가 붙어 있으며 실차 연결 전 제거 대상입니다.

xVehicleMutex가 두 코어를 잇는 유일한 지점이므로, 이 락의 성질이 구조 전체의 안전성을 결정합니다. 현재는 모든 호출자가 구조체를 복사하고 즉시 반납하며 렌더링·전송 같은 긴 작업은 전부 락 밖에서 합니다. 덕분에 실질적 위험이 거의 없습니다. 다만 이는 지금 코드가 그렇게 짜여 있다는 뜻이지 구조가 강제하는 것은 아닙니다. 락을 잡은 채 오래 걸리는 작업을 하는 코드가 나중에 추가되면 이 표의 첫 줄은 즉시 "높음"이 됩니다.

5. 한쪽이 잘못되면 나머지는 어떻게 되는가

담당자가 물었던 "CAN이 들어오는 중에 UI에 오류가 나면"에 대한 답입니다.

상황 CAN 동작 화면 시스템 반응
UI가 느려짐 · 멈춤
(양보 없이 계속 도는 경우)		 정상 계속 얼어붙음 태스크 워치독 5초 → 경고만, 리셋 없음
UI 크래시
(잘못된 메모리 접근 등)		 같이 끊김 꺼짐 패닉 → 칩 전체 재부팅, 약 1.2초 후 CAN 복귀
UI가 뮤텍스를 잡은 채 멈춤 영구 정지 얼어붙음 아무 감지 없이 조용히 멈춤
인터럽트 지연 300 ms 초과 같이 끊김 꺼짐 인터럽트 워치독 → 재부팅
CONFIG_ESP_TASK_WDT_TIMEOUT_S=5이고 CONFIG_ESP_TASK_WDT_PANIC은 꺼져 있어 태스크 워치독은 경고만 냅니다. 반면 CONFIG_ESP_SYSTEM_PANIC_PRINT_REBOOT=y, 재부팅 지연 0초라 실제 크래시는 즉시 재부팅입니다.

재부팅은 오히려 깔끔하게 처리됩니다

두 번째 줄은 걱정할 상황이 아닙니다. UI가 크래시해서 재부팅되면 Alive가 약 1.2초 끊겼다가 uptime 값이 0부터 다시 시작하므로, 인버터 쪽에서 "재부팅했다"를 명확히 구분할 수 있습니다. ClusterAlive의 uptime을 롤오버시키지 않고 65535초에서 고정시킨 결정이 여기서 값을 합니다.

진짜 구멍이었던 첫 번째 줄 — 해결

UI만 멈춘 경우, CAN은 멀쩡하므로 Alive가 계속 정상으로 나갔습니다. 인버터 입장에서 클러스터는 완전히 건강해 보이는데 운전자는 얼어붙은 화면을 보는 상태입니다. CAN 수신이 끊겼을 때 화면을 흐리게 처리하는 기능도 UI가 살아 있어야 그려지므로 이 상황에서는 소용이 없습니다. 즉 CAN으로 내보내는 것 말고는 알릴 방법이 없습니다.

그래서 ClusterAlive의 상태 바이트에 UI 하트비트 비트를 추가했습니다. 렌더링 태스크가 한 프레임을 끝까지 처리할 때마다 시각을 남기고, twai_tx가 500 ms마다 그 값이 1초 이내인지 확인해 bit4에 싣습니다. CAN 수신 끊김을 감지하는 방식과 동일하며 새 메시지도 새 구조도 필요 없습니다.

설계상 두 가지를 일부러 그렇게 했습니다. 하트비트는 lv_timer_handler()가 반환한 뒤에 기록합니다 — 루프 진입 시점에 찍으면 "태스크가 깨어났다"만 보증하지만, 반환 후에 찍으면 "한 프레임을 실제로 끝냈다"를 보증합니다. 그리고 하트비트는 뮤텍스를 쓰지 않습니다 — 감지하려는 상황 중 하나가 "UI가 뮤텍스에 걸려 멈춘 상태"인데, 감지 수단이 같은 뮤텍스를 잡으면 감지하는 쪽도 같이 멈춥니다.

실기기 검증 완료. Kvaser로 0x300을 받아 해석한 결과, 부팅 직후 아직 첫 프레임을 그리지 못한 순간의 status=0x00과 렌더링 시작 후의 status=0x10이 그대로 잡혔습니다. 결함을 주입하지 않고도 양쪽 상태가 실기기에서 확인된 셈입니다.

검증 중에 따로 발견된 것 — 묵은 Alive 방출

0x300을 읽다가 예상 밖의 값을 봤습니다. 카운터는 0부터 연속인데 uptime이 0, 1, 1, 2, 2, 3에서 갑자기 89로 뛰었습니다.

원인은 버스에 ACK를 줄 노드가 없는 동안 Alive가 나가지 못하고 송신 큐에 쌓인 채 재전송을 반복하고 있었던 것입니다. 리스너가 채널을 열자 ACK가 생기면서 89초 전에 만들어진 payload 6개가 한꺼번에 방출됐습니다. Alive에서 이건 단순히 무의미한 정도가 아니라 해롭습니다 — 인버터가 uptime 0을 보고 "방금 부팅했다"고 오판합니다.

직전 Alive가 아직 안 나갔으면 이번 주기를 건너뛰도록 고쳤습니다. 재전송 자체를 끄는 방법도 있지만, 그러면 버스가 붐빌 때 정상적으로 발생하는 중재 실패까지 버려서 Alive 도달률이 떨어집니다. 수정 후 묵은 프레임은 6개에서 1개로 줄었습니다.

남은 1개는 없앨 수 없습니다. 버스가 죽는 순간 이미 하드웨어 송신 버퍼로 넘어간 프레임이라 큐 쪽 조치가 닿지 않습니다. 수신측은 첫 Alive 한 개를 신뢰하지 말고 두 번째 프레임부터 판단하는 편이 안전합니다 — 인버터 팀에 전달이 필요한 사항입니다.

6. 정리

  • 코어 분리가 1차 방어선입니다. 통신(코어 0)과 렌더링(코어 1)이 서로를 밀어내지 못합니다.
  • 코어 0 내부는 우선순위와 하드웨어 큐로 정리됩니다. BLE가 CAN 태스크를 밀어내도 프레임은 ISR이 큐에 넣어두므로 유실되지 않습니다.
  • 수신 부하에는 상한이 있습니다. 어셉턴스 필터 덕분에 실차 버스에 붙여도 초당 15 프레임을 넘지 않습니다.
  • 여유가 없는 쪽은 렌더링입니다. 통신은 확장 여지가 크고, 화면은 이미 예산을 초과하고 있습니다.
  • UI가 멈추면 CAN으로 알립니다. ClusterAlive bit4에 렌더 하트비트를 실어, 화면이 멈춰도 인버터가 알 수 있게 했습니다. 실기기 검증 완료.
  • 인버터 팀에 전달할 사항이 하나 있습니다. 버스 복구 직후 첫 Alive 한 개는 몇 초 전 값일 수 있으므로 두 번째 프레임부터 판단해야 합니다.
